# Нагрузочные проверки — усиленный артефакт (Tree of Thoughts, альтернатива B)

| Сценарий | Нагрузка и длительность | Допустимый предел | Что измеряем | Evidence |
|---|---|---|---|---|
| Baseline (холодный/тёплый старт) | 1–2 rps, 10 мин; первые 2 мин — холодный старт, далее — тёплый | p95 < 400 ms, p99 < 800 ms; error rate < 1% | Latency p50/p95/p99, error rate, CPU < 70%, память стабильна | Отчёт генератора (CSV/HTML), графики latency; системные метрики (CPU/RAM) из мониторинга |
| Ramp to peak | Линейный рост 0 → X rps за 15 мин, X — целевой пик; удержание X rps 10 мин | p95 < 600 ms на плато; error rate < 2%; без резких падений throughput | Throughput, latency на плато, ошибки по кодам | Отчёт прогона с кривой нагрузки и latency, логи ошибок |
| Spike | Мгновенный скачок X → 1.5X rps на 2–3 мин | В течение 60 с после спайка система возвращается к p95 < 700 ms; отсутствие длительной деградации | Время восстановления p95, очереди/пулы | Скриншоты/графики метрик до/после спайка |
| Short soak (короткая пропитка) | 0.6X rps, 60–120 мин | Дрейф p95 не более +20% от первых 10 мин; отсутствие роста memory > +10% | Тренд latency, память, GC/handle counts | Сравнительные графики первых и последних 10 мин, diff отчётов |
| Stress до отказа | Рост X → 2X rps с шагом каждые 3 мин до ошибок > 5% или деградации p99 > 2s | Фиксация «предела» (Throughput*, p99, ошибка); корректное восстановление после снятия нагрузки | Предел пропускной способности, поведение при отказе | Протокол шага нагрузки и метрик, отметка порога отказа |
| Concurrency cap | Ограничение одновременных запросов (например, 50, 100, 200) при постоянной rps | Стабильность latency при росте concurrency до выбранной планки | Latency vs. concurrency, блокировки | Таблицы latency по уровням concurrency, конфиг пула |

Примечания и допущения:
- Значение X — ориентир пикового трафика. Если нет исторических данных, принять X = 10 rps как консервативный старт для стадии; пересчитать после первых метрик. Единица может быть «операций/сек» при отсутствии HTTP.
- Если сервис имеет внешние лимиты (квоты API/БД), зафиксировать их и не превышать без согласования.

Если нагрузочное тестирование пока не требуется, обоснование и условие включения:
- Обоснование: отсутствует стабильная сборка или среда, нет метрик наблюдаемости, нет даже оценочного X. Риск искажённых выводов выше пользы.
- Условие включения: как минимум доступен stage с базовым мониторингом latency и ошибок; определён ориентир X (даже приблизительный), согласованы окна запуска, чтобы не мешать другим.

## Как использовали AI

- Строка в `prompts.md`: «Сформируй 3 альтернативы стратегии нагрузочного тестирования (минимальная/сбалансированная/расширенная), оцени по критериям и сгенерируй таблицу сценариев с порогами и evidence. Вход — артефакты practice_01 (кроме CASE.md/README.md).»
- Что проверили и исправили сами: нормализовали пороги p95/p99, уточнили X и длительности под доступный стенд; исключили длительный soak из первой итерации.
