## Запрос

Роль: опытный инженер по производительности.

Цель: на основе разрешённых источников сформировать таблицу нагрузочных сценариев для сервиса с эндпоинтами `POST /api/reviews` и `GET /health`, учитывая, что обработка `POST /api/reviews` включает синхронный вызов внешнего LLM.

Контекст (источники):
- practices/practice_01/TRAINING_PR.diff — см. `review_service.py` 19–22 (внешний вызов `llm.generate`), `api.py` 35–37 (эндпоинт `POST /api/reviews`), 40–42 (эндпоинт `GET /health`).
- Формат результата — как в practices/practice_01/tests_load.md (строки 1–5: таблица с колонками «Сценарий | Нагрузка и длительность | Допустимый предел | Что измеряем | Evidence»).

Задача: предложить 4–5 реалистичных сценариев, разделив их на:
- быстрый контрольный `GET /health`;
- `POST /api/reviews` со стабом LLM (для изоляции сервиса);
- `POST /api/reviews` с реальным LLM при низкой параллельности (учёт внешних ограничений);
- граничный сценарий по размеру payload (крупный `diff`);
- деградационный сценарий при недоступности LLM.

Для каждого сценария задать: нагрузку (RPS/потоки) и длительность, допустимые пределы (p95/ошибки/таймауты/ресурсы), что измеряем. Использовать формулировки, которые вытекают из архитектуры источников (внешний вызов может доминировать в латентности). Не ссылаться на внешние SLO провайдера. Вывести результат в таблице формата исходного артефакта. Кратко обосновать, почему нагрузочное тестирование требуется сейчас.
