## 2. Сравнение SDD-фреймворков: OpenSpec vs git-spec

| Критерий | OpenSpec (изучался на семинаре) | git-spec (выбран для ДЗ 5) |
|---|---|---|
| **Архитектурный подход** | Файловый workflow на базе Markdown-документов (`proposal`, `specs`, `tasks`, `design`) | Векторная семантическая индексация всей кодовой базы и спецификаций в PGlite |
| **Хранение состояния** | Каталог `.openspec/` со структурированными каталогами изменений | Встраиваемый WASM PostgreSQL (`pglite-data/`) с pgvector |
| **Поиск по контексту** | Текстовый CLI-инструктаж (`openspec instructions ...`) | Семантический векторный поиск по косинусному расстоянию (`git spec query "<запрос>"`) |
| **Командное взаимодействие** | Ориентирован на последовательное изменение одной фичи одним агентом | Поддерживает эмуляцию двух команд (UI и Logic) с фиксацией контракта в репозитории |
| **Интеграция с Git** | Отдельная утилита командной строки `openspec` | Нативная интеграция через механизм Git (`git spec ...` вызывает утилиту) |
| **Устойчивость в brownfield** | Требует ручной поддержки структуры директорий | Автоматически строит граф зависимостей через `git spec parse` |

**Обоснование выбора git-spec:**
Для brownfield-проекта ключевой проблемой является ориентация агента в существующем коде. `git-spec` сочетает построение графа импортов (`parse`) с семантическим поиском по векторному индексу (`index` и `query`). Это позволяет агенту мгновенно находить релевантные контракты и функции без засорения контекстного окна избыточными файлами.

## 3. Эмуляция двух команд и согласование контракта

Перед написанием кода была проведена эмуляция двух команд:
- **Команда 1 (UI / Frontend):**
  - Разработала `specs/frontend.md`.
  - Требования: маска ввода даты `dd-mm-yyyy`, селекты регионов и культур, анимация спиннера загрузки, информативный блок с погодными фактами и вероятностью.
- **Команда 2 (Logic / Backend API):**
  - Разработала `specs/api-endpoint.md`.
  - Требования: тонкая обёртка на FastAPI над `main.py`, валидация Pydantic, сохранение доменных правил `app/config.py`, коды 422 и 502.
- **Согласование контракта (`specs/contract.md`):**
  1. *Формат даты:* UI хотел `dd.mm.yyyy`, API требовал `dd-mm-yyyy` (как в CLI). Договорились о строгом `dd-mm-yyyy` с клиентской маской.
  2. *Коды ошибок:* Согласовали, что неверные параметры дают **422**, а недоступность модели/погоды — **502**.
  3. *Раздача статики:* Договорились, что FastAPI сам раздает статические файлы из `web/` через `StaticFiles`, что устраняет необходимость поднимать отдельный nginx/node сервер для локальной разработки.

## 4. Разбор реализованных артефактов

### 4.1. HTTP API (`app/api.py`)
- Реализован через FastAPI.
- Эндпоинты:
  - `GET /health` -> `{"status": "ok", "ok": true}`
  - `POST /query` -> принимает `QueryRequest`, валидирует дату через `parse_date`, проверяет регионы и культуры через `ensure_region_key`/`ensure_crop_key`, тянет погоду ERA5, запрашивает Ollama и отдает `QueryResponse`.
  - Раздача статики: `GET /` отдает `web/index.html`, `/static` отдает JS/CSS.
- Включен CORS для гибкости развертывания.

### 4.2. Веб-интерфейс (`web/`)
- `web/index.html`: семантическая доступная разметка, подсказки пресетов дат, блок результата.
- `web/styles.css`: аккуратная темная тема, CSS Grid, индикаторы онлайна API.
- `web/app.js`: маска даты, клиентская валидация, конечный автомат состояний (idle -> loading -> success / error).

### 4.3. Окружение агента (`.opencode/`)
1. **`AGENTS.md`:** устойчивые правила Spec-Driven Development, запрет разрушительных Git-команд, изоляция в рамках scope проекта.
2. **Skills:**
   - `git-spec`: управление векторным индексом и поиск.
   - `specs-api`: правила создания FastAPI эндпоинтов.
   - `specs-frontend`: спецификация фронтенда и контракта.
   - `practice05.testing`: методика написания e2e сценариев и локальных проверок.
3. **MCP Server (`.opencode/mcp/server.js`):**
   - Инструменты: `weather.features`, `validate.input` (с кодом 413 при diff > 20000), `api.health`, `spec.query`.
4. **Plugin Hook (`.opencode/plugins/practice05-check/index.js`):**
   - Автоматический запуск `scripts/check.sh` после `write:after`, `edit:after`, `patch:after`.

## 7. Вопросы и ответы на защите

**В: Зачем нужен был общий контракт (`specs/contract.md`), если можно сразу писать код?**  
О: В brownfield-разработке одновременное изменение бэкенда и фронтенда без предварительной фиксации контракта приводит к расхождениям (например, формат дат `dd-mm-yyyy` vs `YYYY-MM-DD`, структура ошибок, имена полей). Зафиксировав контракт до кода, обе части разрабатывались и тестировались независимо, а тест `test_contract_consistency_ui_and_api` подтвердил их 100% совместимость.

**В: Чем git-spec отличается от OpenSpec?**  
О: OpenSpec использует файловую иерархию папок в `.openspec` и текстовые инструкции CLI. `git-spec` использует PGlite (WASM Postgres + pgvector) для семантической индексации проекта в виде эмбеддингов, позволяет выполнять векторные запросы (`git spec query`) и интегрируется прямо в Git через подкоманду `git spec`.

**В: Как гарантируется, что CLI-приложение из Практики 4 не сломалось?**  
О: Доменный код (`app/config.py`, `app/weather.py`, `app/ollama_client.py`, `main.py`) не модифицировался в части логики. Все 12 базовых тестов CLI сохранены и дополнены тестом `test_scenario_cli_local_launch`, проверяющим запуск через `subprocess`.
