Ниже разбор изменений из TRAINING_PR.diff и найденные проблемы (по убыванию критичности), с привязкой к файлам и строкам из диффа.
Проблемы
1. app/api.py:35-38 — отсутствие валидации входных данных
- Код ожидает ключ payload"diff". Если его нет, будет KeyError и 500 вместо 4xx (некорректный запрос).
- Нет схемы запроса/ответа. Использование bare dict ухудшает валидацию и документацию OpenAPI. В FastAPI рекомендуется Pydantic-модель для тела запроса и response_model для ответа.
2. app/api.py:35-38 — отсутствие аутентификации/авторизации
- Публичный POST /api/reviews без проверки прав в проде — риск несанкционированного использования и злоупотреблений (в т.ч. нагрузка/стоимость LLM).
3. app/review_service.py:19-22 — отсутствие обработки ошибок и ограничений при работе с LLM
- Если llm.generate выбросит исключение (таймаут, 429, сеть), это поднимется до 500. Нужны перехват, маппинг на понятные клиенту ошибки и/или retry/таймаут.
- Не ограничен размер diff. Большие PR могут превысить лимит токенов или привести к высоким затратам/задержкам. Нужна усечка/аннотация/пейджинг.
4. app/review_service.py:19-22 — риск утечки чувствительных данных в LLM
- В сыром виде отправляем diff в LLM. Если используется внешний провайдер — риск комплаенса/конфиденциальности. Нужна полиси/маскирование/опция отключения.
5. app/api.py:35-38 — слабая контрактность интерфейса
- Возвращается dictstr, str с единственным ключом comment. Для API ожидаемо иметь стабильную схему с полями id, created_at, возможно список findings. Сейчас схема хрупкая и плохо расширяема.
6. app/review_service.py:19-22 — слабый промпт и отсутствие формата выхода
- "Review this pull request and find problems:" без чётких инструкций/делимитеров. Нет отделения контекста (например, diff ... ), нет требования структуры ответа (список с файлами/строками/серьёзностью). Это ухудшит качество и воспроизводимость результата.
7. app/api.py:35-38 — отсутствие response_model ухудшает OpenAPI
- Без response_model документация FastAPI покажет неопределённый объект, клиенты будут страдать от неявностей.
8. Совместимость и типы
- app/api.py:36-37 и app/review_service.py:19 — используются built-in generics dictstr, str. Это ок для Python 3.9+. Если проект целит 3.8, это упадёт на импорт. Нужен либо typing.Dict, либо from future import annotations, либо гарантированная 3.9+ среда.
- app/review_service.py:9-13 — Protocol импортируется из typing. Это ок для 3.8+, но если ранее проект поддерживал 3.7, нужна typing_extensions.Protocol.
9. Стиль/поддерживаемость
- app/review_service.py:10-13 — изменение объявления метода в Protocol на многострочное с ... не добавляет ценности; pass или однострочник читабельнее и единообразнее.
- Нет логирования (ошибок LLM, метрик длительности/размера diff) — затруднит эксплуатацию и отладку.
- Нет тестов под новый endpoint и сервис.
Открытые вопросы
- Какая целевая версия Python (3.8 vs 3.9+)? Это влияет на аннотации и Protocol.
- Внешний или внутренний LLM используется? Есть ли требования к защите/маскированию данных diff?
- Требуется ли аутентификация/квотирование для /api/reviews?
- Какой формат ответа ожидается потребителями? Нужен ли структурированный список замечаний с привязкой к файлам/строкам/серьёзности?
- Максимальные размеры diff и SLA на отклик?
