### 1. Цель и роль

- Цель: Заполнить содержимое всех Markdown-файлов в репозитории, не изменяя их структуру (заголовки, порядок секций, якоря), используя доступный контекст задачи. Исключения: не изменять `README.md`, `context.md`, `prompts.md`, `P1-02.md`, `CASE.md`, `master-prompt.md`.
- Роль AI: сеньор-разработчик, который структурирует и заполняет документацию на основе фактов из контекста PR.

### 2. Входы и источники

- Обязательные входы: \[context.md], \[TRAINING\_PR.diff].
- Разрешённые файлы и источники:
  - Контекст: `practices/practice_01/context.md`, `practices/practice_01/TRAINING_PR.diff`.
  - Структуры целевых файлов: чтение всех `**/*.md`, чтобы понять текущие заголовки и порядок разделов.
  - Внешние источники запрещены.
- Context Pack — правила и примеры берём из \[context.md]: SEC-1, API-1, REL-1, OUT-1, QA-1, OBS-1, SCOPE-1 и «хороший/плохой пример».

### 3. Задача и артефакты

- Что сделать:
  - Определить список целевых файлов: все `**/*.md`, кроме: `**/README.md`, `**/context.md`, `**/prompts.md`, `**/P1-02.md`, `**/CASE.md`, `**/master-prompt.md`.
  - Для каждого целевого файла заполнить существующие секции контентом, строго опираясь на \[context.md] и \[TRAINING\_PR.diff]. Структуру (заголовки, порядок, уровни, существующие пункты) не менять.
  - Контент делать конкретным: ссылки на строки diff, правила из Context Pack, воспроизводимые проверки.
- Что вернуть: готовые правки файлов (для каждого файла — полный итоговый текст) и сводка по внесённым изменениям.

### 4. Формат результата

- Структура ответа: patch-энвелоп совместимый с apply\_patch:
  - `*** Begin Patch`
  - для каждого целевого файла — блок `*** Update File: <path>` с новым содержимым файла;
  - без блоков Add/Delete, без добавления новых файлов, без переименований;
  - `*** End Patch`.
- Требования к содержимому:
  - Язык: русский.
  - Сохранять все заголовки, уровни и порядок разделов; наполнять только тело секций.
  - Вставлять краткие ссылки на источники в тексте: `[TRAINING_PR.diff: app/api.py 35–38]`, `[context.md: OUT-1]`.

### 5. Полномочия и запреты

- Разрешено:
  - читать `TRAINING_PR.diff`, `context.md`;
  - читать целевые `**/*.md` для понимания структуры;
  - изменять только целевые `**/*.md` (кроме исключений, перечисленных выше).
- Запрещено:
  - изменять или удалять исключённые файлы (`README.md`, `context.md`, `prompts.md`, `P1-02.md`, `CASE.md`, `master-prompt.md`);
  - добавлять новые файлы или менять структуру (заголовки, уровни, порядок);
  - вносить неподтверждённые утверждения, выходить за SCOPE-1, раскрывать секреты (см. SEC-1/OBS-1).
  - читать директории выше `practices/practice_01`, внутренние файлы директории `practices/practice_01` разрешены для чтения в соответствии с предыдущими правилами

### 6. Рабочий процесс и остановка

- Шаги:
  - Собрать список целевых файлов по маске и исключениям.
  - Прочитать \[TRAINING\_PR.diff] и выделить: изменённые файлы, маршруты (`/api/reviews`), интерфейсы и точки риска.
  - Прочитать \[context.md], выписать применимые правила (SEC-1, API-1, REL-1, OUT-1, QA-1, OBS-1, SCOPE-1) и примеры.
  - Для каждого целевого файла:
    - Считать структуру (заголовки/пункты); определить назначение файла по названию.
    - Заполнить секции материалом, подтверждённым diff или правилами. Вставлять минимальные цитаты из diff с отсылкой к файлу/строке.
    - Добавить воспроизводимые проверки (где уместно) — e2e/интеграционные/юнит/нагрузочные — по сути изменений.
  - Сформировать patch-энвелоп без изменений структуры.
- Когда остановиться и запросить человека:
  - если структура файла не позволяет однозначно определить назначение секций;
  - если для очередной секции нет подтверждаемого контента в \[TRAINING\_PR.diff] или \[context.md];
  - если требования противоречат друг другу (например, OUT-1 vs фактический формат ответа).

### 7. Проверки и evidence

- Для каждой секции, где описывается риск или рекомендация, указывать evidence:
  - файл и строка в diff, краткая цитата; ссылка на правило (например, `SEC-1`, `QA-1`, `OUT-1`).
  - пример проверки: что запустить/измерить и ожидаемый результат.
- Сохранять только необходимый минимум цитат; не логировать весь diff (OBS-1).

### 8. Definition of Done

- Задача закончена, когда:
  - все целевые `**/*.md` (кроме исключений) заполнены содержанием на русском языке без изменения структуры;
  - в тексте присутствуют ссылки на источники (\[TRAINING\_PR.diff], \[context.md]);
  - рекомендации и выводы подтверждены diff или правилами (QA-1), соблюдены OUT-1/SEC-1/API-1/REL-1/OBS-1/SCOPE-1;
  - результат предоставлен в виде одного patch-энвелопа `*** Begin Patch` … `*** End Patch` с блоками `*** Update File:` для каждого изменённого файла.

### Подсказки по типовым файлам

- `analysis.md`: краткое summary изменения, до трёх рисков с evidence и предложенные проверки. Источники: [TRAINING_PR.diff], [context.md].
- `tests_unit.md`: юнит-тесты для `ReviewService.review` (обработка лимита длины — по API-1; маскировка секретов — SEC-1; формат OUT-1). Сценарии: короткий diff; длинный diff → отказ; diff с секретом → `[REDACTED]`.
- `tests_integration.md`: интеграционные тесты для `POST /api/reviews` [TRAINING_PR.diff: app/api.py 35–38]; таймаут LLM и контролируемый ответ (REL-1).
- `tests_e2e.md`: сквозной сценарий: запрос с diff → JSON по OUT-1; отсутствие логирования содержимого (OBS-1).
- `tests_load.md`: нагрузка на `POST /api/reviews`, лимиты по длине diff и времени (API-1, REL-1).
- `adr.md`: зафиксировать решение об интерфейсе `/api/reviews`, формате ответа OUT-1 и ограничениях SEC-1/API-1/REL-1.
- `product_management.md` и `project_management.md`: цели, роли, проверки, backlog задач, вытекающих из правил и найденных рисков.
- `problem.md`: формулировка проблемы, контекст и критерии приёмки по OUT-1/QA-1.
